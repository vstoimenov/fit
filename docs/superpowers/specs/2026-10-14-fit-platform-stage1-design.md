# Fit Platform — Етап 1 (ядро + абонамент + админ) — дизайн

Дата: 2026-10-14 · Статус: секциите одобрени в чата, чака преглед на писмения спек
Работно име: `fit-platform` (папка `cloude-c/fit-platform`) — брандът идва по-късно

## 1. Цел и контекст

Абонаментна платформа за онлайн тренировки за **жени 25–40 г.**, един бранд (не SaaS).
Ползва се като мобилно приложение (PWA). Собственикът управлява всичко от админ панел.
Бранд и механизъм още няма — строим функционална база, после я „обличаме" маркетингово.
Вдъхновение от HubFit за функции и UX модели — без копиране на дизайн/бранд.

Изисквания на потребителя, които този спек покрива:
- 3 нива тренировки: Начинаещ / Напреднал / Профи
- Админ календар: поставям няколко линка и задавам дата/час на появяване
- При регистрация — анкета (ръст, тегло, цел, проблем) и 1 безплатна тренировка за начинаещи
- Абонамент; интеграции Stripe и Revolut (бъдещи), Meta Pixel + CAPI, всичко за Google
- Посещения на сайта, кой колко е тренирал, клиентката отбелязва прогрес, админът вижда кой изостава и го „побутва"/звъни
- Модерна, интерактивна, да не прилича на шаблон/AI slop
- Стабилна, защитена професионална платформа

## 2. Ключови решения

| Тема | Решение |
|---|---|
| Модел | Един бранд, един абонамент дава достъп до всичко (месечен + годишен план) |
| Мобилно | PWA (инсталиране на начален екран, push в етап 4), без магазини засега |
| Тренировка | Едно видео „тренирай с мен" (YouTube unlisted линк; поддържа и Bunny, Vimeo) |
| Организация | Седмична програма по нива + библиотека с филтри |
| Календар | Общ за всички в ниво; админът насрочва дата/час; новите първо минават **стартова седмица** |
| Фуния | Анкета → акаунт → безплатна тренировка → „Твоят план" + оферта → плащане |
| Вход | Имейл + парола и Google |
| Известия | Push + имейл (Brevo) — в етап 4 |
| Плащания | Общ слой, адаптери Stripe (пълен, тестов режим) и Revolut Merchant |
| Проследяване | Meta Pixel + CAPI, GA4 + Measurement Protocol, Google Ads, GTM, Consent Mode v2 |
| Стек | Next.js 16 (App Router) + Supabase (Auth, Postgres, RLS) + Vercel |
| Supabase | **Нов проект в нов акаунт на служебния имейл на потребителя.** До тогава — локален Supabase (Docker). Не се ползват bg-explorer/agency-crm. |

**Риск, приет от потребителя:** unlisted YouTube линкът не е истинска защита — споделен
линк се гледа без абонамент. Смекчаване: URL-ът се отдава само при право на достъп,
вграждане без YouTube брандинг. Път за надграждане: Bunny Stream с подписани линкове.

## 3. Архитектура

```
Next.js 16 (App Router) на Vercel
├─ /              публичен лендинг (временен, до маркетинга)
├─ /start         анкета + регистрация
├─ /app/*         клиентската PWA (Днес, Библиотека, Профил, Плейър, Прогрес-чекин)
├─ /admin/*       админ (роля admin + задължителен 2FA)
├─ /api/pay/*     checkout, портал, webhooks (по доставчик)
├─ /api/track     сървърни събития → Meta CAPI / GA4 MP
└─ /api/visit     първостранна статистика за посещения
Supabase: Auth + Postgres + RLS (+ pg_cron в етап 4)
Upstash Redis: rate limiting · Sentry: грешки · Better Stack: uptime
```

Модули с ясни граници:
- `lib/brand.ts` — име, лого, цветове, текстове (единственото място за бранд)
- `lib/video/` — нормализиране на линкове (YouTube/Bunny/Vimeo) + oEmbed метаданни
- `lib/program/` — „днешната тренировка", серии, % изпълнение (чисти функции)
- `lib/risk/` — правилата за „Изостават" (чисти функции)
- `lib/payments/` — интерфейс `PaymentProvider` + адаптери `stripe.ts`, `revolut.ts`
- `lib/tracking/` — събития, `event_id`, дедупликация, съгласие, CAPI/GA4 MP клиенти
- `lib/security/` — rate limit, Turnstile проверка, заглавки/CSP

### Правила
- **Видима тренировка:** `publish_at IS NOT NULL AND publish_at <= now()`. Не е нужен cron за публикуване.
- **Достъп до съдържание:** `kind = free` → всяка регистрирана; останалото → `subscriptions.status IN ('active','trialing')` или `past_due` с `now() < grace_until`, или роля admin. Налага се в RLS.
- **Видео URL** се връща само през заявка, минала RLS проверката; списъците за заключени тренировки не съдържат URL.
- **Днешната тренировка:** в стартова седмица → първата незавършена `starter` по `starter_order`; след нея → най-новата публикувана `regular` в нивото ѝ, незавършена. Ако всички са завършени → „Почивен ден / избери от библиотеката".
- **Серия:** поредни локални дни (по timezone на клиентката) с поне една завършена тренировка; ден без публикувана тренировка в нивото не прекъсва серията.
- **% изпълнение:** завършени / публикувани в нивото ѝ откакто е излязла от стартовата седмица (прозорец 14 дни за риск, 7/30 за табла).
- Смяна на нивото — свободно от профила.

## 5. Клиентският поток и екраните

**`/start` — анкета, по един въпрос на екран, с прогрес бар:**
1. Цел: отслабване / стягане / сила / енергия и стрес
2. Какво те притеснява (мулти): корем, дупе и бедра, ръце, гръб и стойка, след раждане, мотивация
3. Опит: никога / понякога / редовно → задава ниво автоматично
4. Ръст, тегло, целево тегло (плъзгачи)
5. Време: 15 / 20–30 / 40+ мин
6. Телефон (по желание) + съгласие за обаждане
7. Съгласия: обработка на здравни данни (задължително за продължаване, отделно), маркетинг (по желание)
8. Име + имейл/парола или Google → акаунтът се създава накрая

→ „Изграждаме твоя план…" (2–3 сек анимация) → **безплатната тренировка** на цял екран
→ „Завърших" (отключва се след 70% от продължителността) + „Как беше?" + конфети
→ **„Твоят план"**: персонализирано резюме от анкетата, какво получава, планове, CTA
→ ако откаже: влиза в `/app` със заключено съдържание и банер.

**`/app` — мобилно, долна навигация:**
- **Днес:** карта „Днешната тренировка", седмична лента с отметки, серия, обратно броене до следващата публикувана, бутон „Отбележи прогрес"
- **Библиотека:** филтри ниво/време/зона; заключените с катинар → към плащане
- **Профил:** данни, ниво, мини графика тегло/обиколки от чекините, абонамент (портал), изтегли данните ми, изтрий акаунта, изход
- **Плейър:** цял екран, вграден плейър, „Завърших"
- **Чекин:** тегло, талия, ханш, енергия 1–5, настроение 1–5, бележка

**Визуални принципи (анти-slop):** без лилави градиенти, генерични икони в кръгчета и клишета;
типография с характер и кирилица, смели размери, плътни цветове, микро-анимации (Framer Motion),
тактилен отклик, реални кадри. Неутрална, добре направена система, която после се облича в бранда.

## 6. Админ панел `/admin`

- **Календар (основен екран):** месечен/седмичен изглед, карти по цвят на нивото; „Добави няколко" — поставяне на N линка наведнъж, автоматични заглавие/продължителност/картинка (oEmbed), за всеки ниво + дата + час + известие да/не; „Разпредели автоматично" (напр. вт/чт/съб 07:00); drag & drop смяна на дата; статуси чернова/планирана/публикувана; предупреждение за ниво без планирано съдържание след дата X.
- **Тренировки:** списък, търсене, филтри, редакция, подредба на стартовата седмица, преглед като клиентка.
- **Клиентки:** таблица (име, ниво, абонамент, регистрация, последно влизане, последна тренировка, брой); профил с анкета, чекини и графика, история на тренировките, абонамент, бележки; ръчен достъп за X дни (provider `manual`).
- **Активност:** сортиране по тренировки/минути за седмица и месец, серия, % изпълнение.
- **Изостават:** клиентки, отговарящи на поне едно правило (прагове в настройки):
  - няма тренировка от ≥ 5 дни
  - < 50% изпълнение за последните 14 дни
  - платила, но без първа тренировка
  - абонамент `past_due`
  Действия: Обади се (`tel:` само при съгласие), Изпрати съобщение (имейл шаблон през Brevo), Бележка, Отложи 7 дни. Всичко → `client_notes`.
- **Табло:** посещения днес/7/30 дни, уникални, източници (UTM), фуния посещение → регистрация → безплатна тренировка → плащане, нови регистрации, активни абонаменти, MRR, churn 30 дни, най-гледани тренировки.
- **Настройки:** планове и цени, активен доставчик на плащания, Meta Pixel ID + CAPI token, GA4 ID + MP secret, GTM, Google Ads conversion IDs, брандинг, прагове за риск, текстове на имейли.
- **Роли:** само `admin` (дава се ръчно в базата). Модератор — в етап 7.

## 7. Плащания

```ts
interface PaymentProvider {
  createCheckout(user, plan): Promise<{ url: string }>
  createPortal(user): Promise<{ url: string }>
  parseWebhook(req): Promise<NormalizedEvent | null>   // проверява подписа
}
type NormalizedEvent = {
  id: string; type: 'activated' | 'renewed' | 'past_due' | 'canceled'
  userId: string; providerSubId: string; planId: string; periodEnd: Date
  amountCents?: number; currency?: string
}
```
- **Stripe:** Checkout (subscription; карта, Apple Pay, Google Pay), Customer Portal, webhooks. Тестов режим до live ключове.
- **Revolut Merchant:** същият интерфейс. **Преди имплементация** — проверка дали Merchant API поддържа рекурентни абонаменти; при ограничения потребителят се уведомява преди продължаване.
- Активният доставчик — от `settings`. Webhook → запис в `payment_events` (уникален `event_id` = идемпотентност) → обновяване на `subscriptions` → сървърно събитие за проследяване.
- Достъпът тече до `current_period_end` и след отказ. `past_due` → `grace_until = now() + 3 дни`, после заключване.
- Картови данни никога не минават през нашия сървър (PCI SAQ A).

## 8. Проследяване

| Събитие | Кога | Meta | Google |
|---|---|---|---|
| PageView | всяка страница | Pixel | GA4 |
| Lead | завършена анкета | Pixel + CAPI | GA4 `generate_lead` + Ads |
| CompleteRegistration | създаден акаунт | Pixel + CAPI | GA4 `sign_up` |
| StartTrial | завършена безплатна тренировка | Pixel + CAPI | GA4 custom |
| InitiateCheckout | клик „Абонирай се" | Pixel + CAPI | GA4 `begin_checkout` |
| Subscribe/Purchase | webhook `activated` | CAPI | GA4 MP `purchase` + Ads |
| Purchase (renewal) | webhook `renewed` | CAPI | GA4 MP |

- Общ `event_id` за Pixel и CAPI → дедупликация; CAPI с хеширани имейл/телефон, `fbp`, `fbc`, IP, user agent.
- Consent Mode v2: банер (приемам / отказвам / настройки); без съгласие клиентските тагове не тръгват; сървърните покупки се пращат само при дадено маркетингово съгласие.
- UTM, `fbclid`, `gclid` се записват при първо посещение и се свързват с профила → кампания на всяка плащаща клиентка в админа.
- `visits` е първостранна статистика без рекламни бисквитки (анонимен ID в first-party cookie), независима от GA4.

## 9. Грешки и гранични случаи

- Webhook по-бавен от връщането от checkout → `/app/welcome` проверява до 15 сек, после „Плащането се обработва".
- Неуспешно подновяване → past_due, банер „Обнови картата", 3 дни гратис, после заключване; клиентката влиза в „Изостават".
- Невалиден/изтрит видео линк → предупреждение в админа при добавяне; при клиентката „Видеото се обновява".
- Часови зони: `publish_at` в UTC, админът въвежда в Europe/Sofia; „днес" и серии по timezone на клиентката.
- Двойно „Завърших" → уникален индекс.
- Офлайн → кеширана обвивка и последното „Днес" + банер „Няма връзка".
- Error boundaries на ниво маршрут; приятелски екрани за 404/500.

## 10. Сигурност и стабилност

**Акаунти:** потвърждение на имейл; парола ≥ 10 символа; rate limit на вход; Cloudflare Turnstile при регистрация/вход/забравена парола; **задължителен TOTP 2FA за admin** (AAL2, проверява се в middleware и в RLS за админските операции); роля admin само ръчно в базата.

**Приложение:** CSP с nonce (allowlist: собствен домейн, YouTube, Stripe, Revolut, Meta, Google, Turnstile), HSTS, `frame-ancestors 'none'`, Referrer-Policy, Permissions-Policy; rate limiting с Upstash Redis (регистрация, вход, checkout, `/api/track`, `/api/visit`); Zod валидация на всеки сървърен вход; без `dangerouslySetInnerHTML`; Server Actions с проверка на произхода; проверка на подписите на webhooks; ключове само в env, `service_role` само на сървъра.

**Данни:** RLS на всяка таблица; Supabase advisors без предупреждения преди пускане; здравни данни (GDPR чл. 9) — изрично отделно съгласие, минимизация, „Изтегли моите данни" и „Изтрий акаунта"; `audit_log` за всяко админско действие.

**Стабилност:** нощен `pg_dump` през GitHub Actions в частно хранилище (Supabase Free няма бекъпи; препоръка Pro + PITR щом има приходи); Sentry с известия при грешка в webhook; Better Stack uptime; CI на всеки push (typecheck, lint, unit, интеграционни, E2E, `npm audit`); preview + production среди; версионирани миграции, без ръчни промени по базата.

**Преди пускане:** security review на кода + ръчен тест по OWASP Top 10: чужди данни, платено видео без абонамент, фалшив webhook, XSS в полетата, брутфорс на вход, ескалация до admin.

## 11. Тестване (TDD)

- **Unit (Vitest):** `lib/program` (днешна тренировка, серии, % изпълнение), `lib/risk`, `lib/video` (нормализиране), адаптери за плащания с примерни webhook payload-и, `lib/tracking` (event_id, дедупликация, съгласие).
- **Интеграционни (срещу локален Supabase):** RLS — неабонирана не вижда платено видео/URL; клиентка не чете чужди редове; не-админ не пише в админски таблици; admin без AAL2 е отказан.
- **E2E (Playwright):** анкета → безплатна тренировка → Stripe тестово плащане → отключено съдържание; админ насрочва тренировка → появява се в часа; чекин → вижда се в админа; клиентка без тренировка 5 дни → в „Изостават".
- **Ръчна проверка в браузъра** на мобилен изглед за всеки екран.
